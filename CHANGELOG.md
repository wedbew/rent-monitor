### Added
- Support refunds and invoices (RM-229): `POST /api/admin/billing/purchases/{id}/refund` (admin only) refunds an **unused** pack in full: it freezes the lot under the user lock, writes a durable refund intent, then asks Paddle; a pack with spent or running units goes to manual review (409 `REFUND_NEEDS_REVIEW`, nothing sent); an ambiguous result is reconciled by listing the transaction's adjustments before any second creation; units move only when Paddle reports the refund approved, a rejected one unfreezes the lot. `GET /api/billing/purchases/{id}/invoice` returns a short-lived Paddle invoice link to the buyer only (no-store, 10 per minute; foreign ids 404). New problem codes `PURCHASE_NOT_REFUNDABLE`, `REFUND_NEEDS_REVIEW`. No migration
- Provider refunds and chargebacks (RM-219): adjustment notifications, and a reconciliation pass every 15 minutes for 60 days after a grant, now apply to a granted pack. A full reversal (approved refund and/or chargeback, counted once) freezes that pack's lot, takes its still-available units back with an append-only `refund_revoke` ledger entry (the balance never goes negative; signup, admin and other packs are untouched) and marks the purchase `refunded`; units held by running audits are revoked when each is released, and units already spent put the account on a **billing hold** (`credit_account.billing_hold`) instead of a debt: new reservations and purchases answer 403 `BILLING_HOLD` until an admin clears it (`POST /api/admin/users/{id}/billing-hold/clear`). A reversed chargeback restores exactly what it took, once (`refund_restore`). Partial refunds, open requests and chargeback warnings freeze the lot and surface `review`; credits and tax corrections remove nothing. Migration `0012` (expand-only): new credit reasons, `billing_hold`, lot reversal markers, `billing_adjustment`. Erasing an account that bought a pack no longer fails: the purchase (an accounting record) drops its reference to the erased ledger row first. Operator action: run `make migrate`
- Paddle webhook and grant (RM-218): `POST /api/webhooks/paddle` verifies `Paddle-Signature` on the raw body (5 s tolerance, secret rotation via `PADDLE_WEBHOOK_SECRET_PREVIOUS`, 256 KiB cap) before anything is parsed, stores the event durably (migration `0011`, expand-only: `billing_event`, unique per environment and event id) and answers 200 for duplicates and 5xx on a database failure; it is the only route exempt from the Origin check, now by exact path. Billing jobs on the ops lane (`process_billing_events`, a one-minute `billing_sweep`) lease pending events (`SKIP LOCKED`), read the transaction fresh from Paddle and grant the pack's own report count exactly once (`paddle:{env}:{txn}:grant`, a lot linked to the purchase) only when price, quantity one, PLN total, no discount or subscription and our binding token all match; anything else is `review`. Missed notifications, ambiguous creations and a dead worker are recovered by reconciliation; a transaction refunded before its grant grants nothing. New problem code `INVALID_WEBHOOK_SIGNATURE` (400), settings `PADDLE_WEBHOOK_SECRET_PREVIOUS`, `PADDLE_WEBHOOK_TOLERANCE_S`, `RETENTION_BILLING_EVENT_DAYS` (90). Operator action: run `make migrate`; register the notification destination in Paddle only with the sandbox first (docs/PADDLE-INTEGRATION.md section 2)
- Report-pack checkout (RM-217): `GET /api/billing/packs`, `POST /api/billing/checkout` (body `{pack_code}` plus an `Idempotency-Key` UUID; 5 per minute and 20 per hour per user), `GET /api/billing/purchases` and `/{id}` (own purchases only, foreign ids 404). Migration `0010` (expand-only): `billing_pack` (immutable catalog versions) and `billing_purchase`. The intent is committed before Paddle is called; one transaction per request key; a creation that timed out is recovered by its purchase reference and binding token and never repeated. New problem codes `BILLING_UNAVAILABLE` (503, billing off: the default), `IDEMPOTENCY_CONFLICT` (409), `BILLING_PROVIDER_ERROR` (502). Nothing is granted yet (signed webhook: #218). Operator action: run `make migrate`; sales stay off until `BILLING_PROVIDER=paddle` and the owner-approved catalog are set

Every grant (signup, admin, later purchases) gets a lot; a reservation holds units from the oldest spendable lots and a release returns them to the same lots; existing balances become one explicit `migration` lot per account (granted = balance + in-flight + consumed + operator-removed, in-flight reservations get allocations).
